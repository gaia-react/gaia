# Changelog

All notable changes to GAIA React are documented here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

- **Major**: breaking changes to skill/command API, Node/React/React Router major bumps.
- **Minor**: new skills, commands, or wiki concept pages; opt-in features, removed or renamed `.claude/` paths.
- **Patch**: bugfixes, docs, and in-range dependency bumps.

## Adopter-action convention

A release change that requires the adopter to act, run a command or hand-migrate, is authored as a `### Removed` or `### Changed` entry carrying an explicit **Action required:** line and/or a literal command to run (for example, `pnpm remove <pkg>`). That exact phrasing is the deterministic anchor GAIA's two CHANGELOG consumers key on: `/update-gaia` cross-references it during a merge to surface a documented, opt-in cleanup suggestion (it never auto-removes a dependency or deletes a file, the adopter decides), and the maintainer-only `release-notes` skill keys on it to tell an agent-automated cleanup (reframe as a benefit or drop) from a human-must-act migration (keep, plainly framed, with a pointer to the steps). Keep the marker and command literal so both consumers match the anchor instead of free-parsing prose. The `react-router-dom` removal below is the worked example. `/update-gaia`'s confirm gate shows the full baseline-to-latest CHANGELOG range, so an adopter several versions behind sees every intervening entry.

## [Unreleased]

### Added

- a filer can now record that a tech-debt fix should ride another change rather than be drained on its own, with a `fold:required` label the drain shows you at the moment you pick what to work on. Some repairs are a sentence of work sitting behind a cost the repair itself does not justify: editing a file the audit gate treats as global discards every reviewer's incremental anchor across the whole repository, so that sentence is nearly free if it rides a change already paying the price and expensive if it does not. Filers were already writing exactly that instruction into issue bodies, in prose, and it reached nobody: the backlog ordering and the related-issue clustering are deliberately model-free, so they read fields and skip prose, and the instruction was honored only when a human happened to notice it. The new label is display-only and gates nothing. It shows up in `/gaia-debt list`, in `why`, and in the description of that issue's option when the drain asks which item to take, so the intent reaches the person making the choice. It could not have been a clustering rule instead: which change should carry the repair depends on what that other change touches, which nothing in the folded issue's own fields can know. Nothing is filtered, parked, or reordered, and an issue carrying the label drains normally when you pick it (#1424)

- work handed to a subagent no longer disappears silently when its reply never arrives. An agent asked to report its findings in its reply has exactly one delivery channel, and when that channel drops, the caller is left holding nothing, which reads exactly like an agent that found nothing worth reporting. That is the one conclusion a caller must not draw, and the failure is biased toward drawing it: dispatch three agents and lose all three and you notice, dispatch eight and lose one and you do not, so the loss that stays invisible is the one that quietly changes the answer. GAIA's spec and plan flows already avoided this by having each agent write its result to a file and return only a short digest, but that contract was written into those two flows as step-by-step instructions rather than stated anywhere as a general convention, so a dispatch composed in the moment inherited none of it. A short rule now states the convention, and the no-op detector gained a general-purpose check the rule points at, so a caller verifies the artifact on disk instead of trusting the reply. The check accepts a count the caller already knows, because a truncated write parses cleanly and reads as a complete result otherwise, which recreates the same ambiguity one level down inside a file that does exist. Because the artifact is on disk, a caller can also read it on its own schedule rather than waiting on a completion signal that may never come (#1409)

- the finding-class vocabulary now names root causes that recur on any codebase, an over-broad assertion, prose that disagrees with the code it describes, a stale count, a guard armed too narrowly, a scan that misses its own input, or a diagnostic that names only one cause of several, so findings of those shapes become countable and actionable instead of landing in an unclassified pile. The workflow-security classes the schema already carried are now assignable, because the audit member that owns them names them. The unclassified recurrence nudge can now be discharged: recording it silences it until fresh evidence raises the count, so closing the vocabulary gap stops the nagging instead of prolonging it. **Action required:** if you have customized `.claude/agents/code-audit-frontend.md`, `/update-gaia` writes the drifted file as a `.gaia-merge` patch and skips it rather than overwriting your customization, so your clone keeps a ten-member holistic list against a bundle that now carries sixteen; apply that patch so your member's vocabulary mirror matches the bundle it assigns against

- a check now stops a regex escape that means two different things depending on which machine runs it. POSIX leaves a backslash before a letter undefined in an extended regular expression, and the two `grep` implementations this project runs on resolved that freedom differently: BSD `grep` on macOS expands `\r`, `\t`, and `\d` into a carriage return, a tab, and a digit, while GNU `grep` on the CI runner matches the bare letter instead. A pattern authored and verified on a laptop therefore inverts on the runner, and it inverts in the worst available direction, toward a check that quietly passes having matched nothing. That is not hypothetical: it was the most serious finding of the round that prompted this, where a `\r?` written to tolerate Windows line endings silently stopped matching what it was written for, and three green deterministic checks ran over that code without one of them seeing it. The new check flags every backslash-escaped letter in an extended-regex `grep` pattern across the project's own shell, its CI workflows and composite actions, and the workflow templates adopter CI renders from, and it names the portable spellings to use instead. It allows the six escapes both implementations were measured to read identically, so the existing call sites relying on those are untouched, and it demands a rewrite for everything else, including the letters the two happen to agree on today, because that agreement is a coincidence of two implementations rather than a promise either one makes. Maintainer-only and release-excluded, so no adopter clone is affected (#1413)

- filing a tech-debt issue now checks its own metadata before the issue is created, and stops rather than filing something a drainer will trip over weeks later. Every rule the check enforces was already written down, and every one of them was being broken anyway, because a label set is the one part of a filing nothing reads back: an issue filed with no severity label silently sorts into the lowest band, and an issue filed carrying the one-time pre-provenance rollout marker destroys the only distinction that marker exists to draw. The check verifies the label vocabulary and counts, the dedup key's shape, and that no label belonging to a later stage of the issue's life has been applied at filing time. It runs offline, so it costs one local call and cannot fail for a reason outside the filing. It also has advisory modes that audit one issue or sweep your whole open backlog, and those change nothing on their own, since repairing an existing issue is a decision per issue. What it deliberately does not check is whether a difficulty grade was chosen honestly: that is a judgment about code, so the mechanical half is enforced and the rubric half stays yours. Because the check sits in front of every filing, it is pre-approved in the settings your clone merges on update, so it runs without interrupting the flow to ask; it reads one local file and a label string, makes no network call, and writes nothing

- tech-debt issues now carry a label recording who can observe the defect, `surface:adopter` or `surface:maintainer`, alongside the severity and difficulty labels. Severity says how bad a defect is and difficulty says how much design its fix needs; neither answers whether anyone outside the project can see it, which is the question that decides whether a backlog item is a user-facing problem or internal housekeeping. Both labels are created idempotently like the others, and the filing check above requires exactly one of them, so the distinction is enforced rather than remembered. Issues filed before this change carry no surface label and nothing relabels them; the advisory sweep will list them if you want to work through them

- the CI workflows GAIA generates for your repository now pass every GitHub-supplied value into their scripts as data rather than pasting it in as text. Actions substitutes a `${{ }}` expression into a `run:` block before bash ever parses it, so a value carrying a quote or a backtick is read as shell syntax; binding it on the step through an `env:` block leaves bash seeing only a variable reference. Nine expressions across the update-deps, stale-branches, and pnpm-audit workflows and the shared auto-merge step were converted. Nothing exploitable was closed: every value involved is one GitHub itself supplies, the repository name or the default branch. What was wrong is that the safety rested on an unwritten promise about each of those values, which nothing enforced and which your clone inherited along with the workflows, one distribution hop past anywhere this project's own review could see it. The existing check for this pattern, until now limited to GAIA's own CI, covers the templates your workflows render from as well, so a later edit cannot reintroduce the shape. Your rendered workflows pick this up on your next `/setup-gaia --reconfigure`; what they do is otherwise unchanged (#1388)

- a check now stops a workflow value from being pasted into a CI script as code rather than passed as data. GitHub Actions substitutes a `${{ }}` expression into a `run:` block's text before bash ever parses it, so a value carrying a quote, a backtick, or a newline is read as shell syntax; binding it on the step through an `env:` block instead removes the hazard entirely, because bash then only ever sees a variable reference. Twenty-two expressions across three workflows were converted. Nothing exploitable was closed: every value involved was either a path the workflow's own scripts produced or a value GitHub itself supplies. What was wrong is that the safety depended on an unwritten promise about whatever produced each value, that it would never emit a shell metacharacter, which nothing enforced and which every later edit to those producers silently inherited. The new check demands the `env:` form uniformly rather than keeping a list of values judged safe, because such a list restores exactly the case-by-case judgement whose absence of enforcement was the defect, and it locates `run:` bodies structurally so the very form it prescribes is not itself flagged. Maintainer-only and release-excluded, so no adopter clone is affected (#1287)

- the pre-merge workflow now reads the whole CI check list it was already fetching, instead of keeping one row and discarding the rest. The step that decides whether the audit has run pulls every check on the pull request and then greps away everything except the audit's own row, so a red check sitting beside it is thrown away unread. That red gets found later, typically after an audit round has already been spent, and repairing it moves the branch, which invalidates the clearance just earned and buys another round. This is not a new step; it is the answer already in hand. The pre-dispatch verification now says to read all of it and fold any red into the same repair batch as everything else found before dispatch, and the same reading is bound to every re-spawn between rounds, which is where it pays most, since each repair commit can red something new while the next round is already being paid for. The guidance carries the four conditions that keep the reading honest: the list describes the pushed commit rather than the tree about to be audited, pending is not a reason to hold the round, a red can be a flake wanting a re-run rather than a fix, and a branch with no pull request has nothing to read and is not an error. Maintainer-facing process guidance on a shipped wiki page, so it reaches adopters on their next `/update-gaia` (#1431)

- the pre-merge self-verification step now covers the prose a comment carries, not just the mechanisms a change adds. A comment asserting something about the repository, that a pathspec covers every surface or that no other caller does a thing, is a question with an answer, and answering it costs seconds against the price of an audit round that finds it wrong. The guidance now says to run that query or delete the sentence, to give a corrected comment the same scrutiny as the one it replaces, and to prefer a test over prose wherever the claim is about what a guard catches. Maintainer-facing process guidance on a shipped wiki page, so it reaches adopters on their next `/update-gaia` (#1385)

- adding a GAIA hook now states what else that obligates, instead of leaving it to be discovered from a red CI job. Every `.sh` under `.claude/hooks/**` needs a matching entry in `.gaia/hook-scopes.json`, and a library under `.claude/hooks/lib/**` additionally needs a tier in the audit reset-predicate partition, but neither requirement appeared anywhere an author reads: both lived only inside the checkers that enforce them, which belong to no quality gate and to no agent's oracle set. A path-scoped rule now names both obligations, and the command that verifies each, at edit time rather than after the push. Maintainer-only and release-excluded, so no adopter clone is affected (#1377)

- the pre-merge fix loop now says to land a whole audit round's fixes in one commit rather than one commit per finding. Each commit rotates the reporting member's content digest and buys a re-dispatch to re-earn its marker, so a round repaired finding-by-finding pays for as many re-audits as the round had findings and clears no more than the single batched commit does. The page already named this failure mode and licensed accepting a finding instead of folding it in, but said nothing about how many commits a round takes, which is the part that was costing the rounds. Maintainer-facing process guidance on a shipped wiki page, so it reaches adopters on their next `/update-gaia` (#1356)

- a test suite that nothing ran now runs in CI, and a suite in that position can no longer hide. Twelve assertions pinning the countable-findings contract across the five audit member definitions, a wiki concept page, and three CLI sources sat in a directory the shard runner's six-directory seam does not reach, so no workflow executed them and a regression in that contract would have merged green. The suite moves in beside its sibling prose pins, where an existing shard picks it up with no seam change, and the wiki page it reads joins the workflow's changed-paths filter so an edit to that page alone re-runs it instead of skipping every test step. The gap was invisible by construction: the sharder's own partition checks compare its shards against a re-listing of the same six directories, so a suite outside all six is absent from both sides of that comparison and every assertion passes while the file runs nowhere. A new check now compares the shards against the repository's own list of every tracked suite, and any suite no shard resolves must name the runner that does execute it, with that runner's continued existence checked rather than trusted. Maintainer-only and release-excluded, so no adopter clone is affected (#1345)

- seven Claude Code hooks now have behavioral test coverage, two of them guards whose whole job is to deny a forbidden edit. A hook of this shape fails silently in the one direction that matters: a logic slip leaves it exiting zero, printing nothing, and letting the write it exists to block simply succeed, so a dead guard looks exactly like a guard with nothing to do and can stay dead indefinitely. The lockfile-edit block, the vitest-globals tsconfig block, and five advisory or session hooks now each have a suite that drives the real hook with a crafted payload and asserts both that it fires and that it correctly abstains, and every suite was first checked against a deliberately broken copy of its hook, so the coverage is demonstrated rather than assumed. No hook behavior changes here; this is the proof that the existing behavior is still there. Maintainer-only and release-excluded, so no adopter clone is affected (#1315)

- the release leak check now runs on every pull request, rather than only when the change happens to touch one of the distribution harness's declared inputs. That harness validates the entire shipped bundle, but it was gated behind a nine-path filter, so a pull request changing any other file that ships resolved the gate false, skipped the harness, and reported green having validated nothing; the leak then surfaced at the release tag instead, where it is far more expensive to fix. The gap was live rather than latent: a comment naming a maintainer-only path, added to a workflow file that ships, did exactly this, and was caught only because the same pull request happened to also touch the harness's own workflow. Closing it meant deciding whether an expensive suite runs on nearly every pull request, and the answer taken here is to split the cheap half out. Staging the tree and running the leak checks over it is about a second of work, so it gets its own job with no path filter at all: the only allowlist that honestly describes what it reads is every file the release does not exclude, and the complement of that is a denylist shape this repo rejects in two separate checks. The seventeen-scenario suite, which is the expensive part, keeps its narrow filter. Maintainer-only and release-excluded, so no adopter clone is affected (#1314)

- a pre-merge check now asserts that a step gated on a changed-paths filter can actually see its own inputs, closing a class of false green that had recurred seven times and been caught by hand every time. Such a step runs only when one of its filter's globs matched the pull request, so if the step reads a file the filter does not list, a pull request touching only that file skips the step and the job reports green having run nothing. On a required check that green is what branch protection reads, and it is indistinguishable from the outside from the green a genuinely irrelevant pull request earns, which is why every instance so far was found by reading rather than by failing. The check compares the two sets for every gated step, and it found live instances on its first run: the shared setup action that three required checks invoke was listed in none of their filters, and neither were the runtime pin and install settings that action reads, so a change to how those checks install and build would have merged with every one of them green having exercised it zero times. Those filters are widened here, as is the fourth required check's hand-rolled equivalent. The check is deliberately a floor rather than a complete accounting, since a shell body can read anything: paths reached only through a script a step invokes, paths assembled at runtime, and the bodies of composite actions stay out of scope, and a workflow that computes its own changed-paths verdict instead of declaring globs is exempt by name so that a second one cannot be introduced silently. Maintainer-only and release-excluded, so no adopter clone is affected (#1313)

- the release build now catches a dangling workflow reference inside a shipped composite action. The check that fails the build when a shipped file names a maintainer-only workflow an adopter never receives scanned the workflow directory but not the composite actions those workflows invoke, even though the sibling path check beside it already treats that directory as a shipped surface. A composite action's description naming such a workflow therefore reached adopters as a pointer to a file their clone does not have, and nothing failed. Nothing in the tree names one today, so this closes a latent gap rather than fixing a live leak; the check runs inside `gaia-maintainer release scrub` and is release-excluded, so no adopter clone is affected (#1306)

- the pre-merge Code Audit Team now has a completeness check, so a file no auditor owns can no longer merge unnoticed. The roster maps file globs to auditor members and the merge gate requires a clearance from every member a change dispatches, but nothing asked the inverse question: which paths dispatch nobody. Such a path resolved an empty member set, which the gate reads as "nobody is owed a clearance", so it merged having been reviewed by no one, and it did so invisibly, because an empty set is equally the right answer for a change genuinely outside every member's remit. Every tracked file must now either resolve an owner or be declared in a new `unowned:` list beside the roster, and that list is checked rather than trusted: an entry reaching a path some member already owns is rejected, as is one no unowned path needs, so a blanket exemption cannot pass and the list cannot quietly accumulate. The Playwright suite and the root tooling that decides what runs (registry config, the pre-commit format and lint config, the container build, the Node version pin, the environment sample) now belong to the default member, so a pull request touching them needs its clearance where it previously needed none. Running the checker by hand on your own clone additionally reports GAIA's own machinery as unowned, which is accurate there rather than a fault, and you clear it by adding `.gaia/**` and `.claude/**` to your `unowned:` list alongside whatever else your tree legitimately leaves unowned (#1245)

- a wiki landing now leaves your local base branch up to date instead of quietly stale. The landing opens its pull request and queues auto-merge, but the merge gate routinely outlasts any wait that fits in a single call, so the throwaway branch and the base branch it was cut from would sit behind until someone noticed and fixed them by hand. `/gaia-wiki` now waits in-session for the merge and finishes the local catch-up when it lands, capped by `GAIA_WIKI_AWAIT_CEILING_SECONDS`; setting that to `0` disables the wait entirely. Independently of the wait, the session-start janitor makes one bounded `git fetch --prune` of your own configured `origin`, and only when a local wiki-sync branch is actually present, so an ordinary session makes no network call at all; it is bounded at 5 seconds by default, rate-limited between sessions, and `GAIA_WIKI_FETCH_TIMEOUT_SECONDS=0` turns it off. It then fast-forwards the base branch with `--ff-only` when you are on base with a clean working tree, which can only advance base to a commit the remote already has, and it reports the refusal rather than skipping silently when it cannot, so an outstanding catch-up is something you are told about instead of something you discover

- the 7-day release-age window now states outright that a version breaching it has to be decided rather than admitted, instead of leaving that to a pnpm default. Both workspace files set `minimumReleaseAgeStrict: true`, and the drift guard already watching the window asserts it on both sides, so weakening it takes a deliberate edit a reviewer sees rather than a one-character one. Installs behave exactly as before on pnpm 11, which already infers strict enforcement wherever a release-age window is set; this pins that behaviour where the policy is written rather than leaving it resting on a default that could move. The setting is also now one `/update-gaia` carries, so it reaches existing adopters on their next update. Note the flag is pnpm 11 only, and pnpm 10 does not need it: the silent-admission behaviour it closes arrived with pnpm 11, so on pnpm 10 a breach of the window already fails the install and the setting is simply inert (#1208)

- the pre-merge Code Audit Team now reviews the CLI's own test and lint tool configs. No member's file ownership reached `.gaia/cli/vitest.config.ts`, `.gaia/cli/eslint.config.mjs`, or `.gaia/cli/prettier.config.mjs`, so a pull request whose only change was one of them dispatched no auditor, required no clearance, and merged with nobody responsible for it. The vitest config is the sharpest of the three, since the setup files it names run on every CLI test run. The Node member takes all three, alongside the rest of the CLI's build and config surface it already owns; the repository-root config files are unaffected and stay with the default member. Maintainer-only and release-excluded, so no adopter clone is affected (#1244)

- the pre-merge Code Audit Team now reviews the CLI workspace's supply-chain policy. No member's file ownership reached `.gaia/cli/pnpm-workspace.yaml`, so a pull request whose only change lowered the minimum release age, dropped the trust policy, or added an exclusion entry dispatched no auditor, required no clearance, and merged with nobody responsible for it. The Node member takes it, alongside the rest of that workspace's dependency surface it already owns; the root workspace file is unaffected and stays with the default member. Maintainer-only and release-excluded, so no adopter clone is affected (#1207)

- the pre-merge audit guidance now names the mutation-restore hazard and asks for a stopping rule before each round. Proving a guard means mutating its logic and putting it back, and the restore discards every uncommitted change to that file rather than only the mutation, so work unrelated to the guard disappears with no diagnostic; the guidance now says to commit first or mutate in a scratch worktree, which is what the audit members already do. It also resolves a tension the page carried: the fix loop said to re-audit until clean while the cost guidance beside it licensed accepting a finding instead, with nothing saying how to choose. That choice now has to be written down before the round runs and has to name an outcome for every way the round can come back, including a new defect in the logic the change itself authored, since deciding once a finding is already on the table reliably answers "one more round". Maintainer-facing process guidance on a shipped wiki page, so it reaches adopters on their next `/update-gaia` (#1226)

- a local rate card for models GAIA has not shipped a price for yet. When Anthropic releases a model, GAIA's cost figures price that model's share at zero until a GAIA release ships its rate, and the shipped rate file is one `/update-gaia` overwrites, so editing it either gets clobbered or turns into a conflict on every release afterwards. You can now add rates to `.gaia/local/token-rates.local.json` instead: it is machine-local, it survives every update untouched, and it merges over the shipped rates per model rather than replacing them. When a model has no rate, the cost readout now prints the exact file and the entry to paste. `/gaia-fitness` gained a cost-rate check that finds such models and offers to write the entry for you, always after showing you the rate it looked up and asking, because a wrong price is worse than a missing one. Reaches existing adopters on their next `/update-gaia` (#1089)

- maintainer-only measurement of Code Audit Team re-spawns. The spawn oracle now records why each member is dispatched, and a reporting command turns the accumulated records into a count of clearances lost to a peer's merge rather than to a real content change, so the decision to re-key the marker can be made on evidence instead of anecdote.
- a filed tech-debt issue now records the work that surfaced it, so a triager reading the backlog months later can tell which branch was under review, what that work was doing, and whether the cited file was one the reviewed change had already touched. The record is an HTML comment, so nothing changes in what a human reads on the issue, and it is diagnostic only: nothing matches on it, nothing gates on it, and a filing is never blocked because a field could not be determined. **Action required:** the backlog that predates this record carries no line to distinguish it from a write that failed, so run this once, per repository, at the point this change goes live there:

  ```bash
  gh label create debt:pre-provenance --color ededed 2>/dev/null || true
  gh issue list --label tech-debt --state open --limit 1000 --json number,body \
    --jq '.[] | select(((.body // "") | test("<!-- gaia-debt-origin:")) | not) | .number' \
  | while read -r n; do
      gh issue edit "$n" --add-label debt:pre-provenance
    done
  ```

  Skipping it costs you only the ability to tell "filed before this change" apart from "the record failed to write" in your own backlog; nothing breaks, no displayed count changes, and the marked cohort drains on its own as the backlog turns over. Re-running the command is safe and is the recovery path for a run that fails partway. Note that this changes the audit agent definitions, which invalidates any clearance already earned on an open pull request; re-run its audit members before merging.
- the sandbox conformance suite now runs in CI. Nothing executed that tree of tests, so a failing assertion in it blocked no merge and could sit on the main branch indefinitely, which is how a stale assertion about a permission rule survived there until someone opened the file for an unrelated reason. It runs behind its own path filter rather than joining the existing one, because one of its checks reads every documentation and configuration file in the repository: as a separate filter, arming it costs a test step instead of two dependency installs and the concurrency meter. Two checks self-skip by design, the one needing a sandbox-capable machine and a documentation-link reachability check that would otherwise let a third-party outage block every merge in the repository, and the tests README now states for each tree whether CI gates it or a human runs it. One assertion was removed rather than wired in: it required history a CI checkout does not fetch, asserted something untrue of the repository, and contradicted another required check that instructs you to do the very thing it forbade. Also fixes the suite runner's fallback installer, which named a package that does not exist and so failed instead of falling back. Maintainer-only and release-excluded, so no adopter clone is affected (#1079)
- Serena's `activate_project` call is now guarded against silently activating a different checkout of the same clone. Working in a linked worktree while Serena is registered without automatic per-directory activation, a bare project name resolves through Serena's own global registry to the main checkout with no error, so every symbol lookup afterward answers from the wrong tree's files; the guard now refuses that activation and names the worktree's own path to use instead.
- the pre-merge Code Audit Team now reviews the husky commit hooks. No member's globs matched `.husky/**`, so a pull request changing `.husky/pre-commit` alongside any other owned surface dispatched auditors for the other files only and the hook itself merged with nobody responsible for it, even though it is the Quality Gate floor for every commit and a change to it can silently disable typecheck, lint, and tests for a whole class of commits. The shell member takes it: the hooks are extensionless POSIX shell that no `*.sh` glob reaches, it already holds the shellcheck oracle, and it is advisory-only, so it can never repair the very gate that would catch its own bad repair. Maintainer-only and release-excluded, so no adopter clone is affected (#1008)
- the pre-merge spawn oracle now warns when the branch has fallen behind `origin/main`. A branch that drifts behind main during a long run audits clean, and the rebase it then needs in order to merge pulls main's changes into files the audit roster owns, rotating those members' content digests and invalidating every marker the audit just earned, so the whole round is spent again. The oracle already runs immediately before every dispatch wave, so it now names the commit count and advises rebasing first; it never blocks, never changes the member set it emits, and does no network fetch, so a deliberate audit of an older tree still works and the oracle stays offline-safe. Maintainer-only and release-excluded, so no adopter clone is affected (#1010)
- the PR Merge Workflow now tells the operator to verify an audit Suggestion's technical claims before applying it. The existing guidance prices the re-audit a fix costs but assumes the Suggestion is right, and a member can assert a mechanism it inferred rather than verified; implementing such a claim verbatim turns a reviewer's error into documented guidance that reads as reviewed. The content digest still forces a re-review of the applied fix, so this buys one round rather than closing a hole (#986)
- passing your own deterministic checks is now stated as the entry condition for dispatching the pre-merge audit team, rather than something the audit discovers for you. Every dispatched member costs real time and budget, so a defect you could have caught yourself spends the round that should have gone to what you cannot see, and two or three rounds spent that way is the ordinary failure. The guidance now names what to run first, and corrects what proving a new guard takes: breaking the thing a guard watches only proves the fixture, while mutating the guard's own logic is what proves the assertion, and a change that adds two mechanisms needs both mutated separately or the second one ships unproven (#1030)
- each Code Audit Team member's declared file ownership is now generated from `.gaia/audit-ci.yml` instead of hand-transcribed into its agent definition, so the two can no longer drift. The roster check fails whenever a member's generated remit disagrees with the roster entry that dispatches it, and every such failure names the one command that repairs it, `bash .gaia/scripts/write-audit-remits.sh`. Both the check and the writer are run by hand on an adopter clone (#978)
- the Playwright conventions rule now documents how to assert that a page load produced no errors. ### Changed

- a tech-debt issue's handler class, whether its fix is a prompt, a plan, or a design SPEC, is now a `handler:prompt` / `handler:plan` / `handler:spec` label instead of a `Handler:` line buried in the issue body. It was the last of the four classification axes carried as prose while severity, surface, and difficulty were all labels, and prose cost it three things a label has for free: you can now filter the backlog with `gh issue list --label handler:spec`, a body someone reformatted by hand no longer parses as no class at all, and re-grading is a one-command relabel whose before-and-after GitHub records in the issue timeline. That last one matters most, because the class is advisory by design: `/gaia-debt` re-derives it from the cited code at drain time and can move an issue in either direction, so the field most likely to be changed was the one that was hardest to change. The label is validated when present and never demanded, so a hand-filed issue that carries no class stays legal and drains exactly as it does today. New filings carry the label and no body line. **Action required:** run the one-time backfill in `.claude/skills/file-tech-debt/SKILL.md` (`## Rollout: backfill the handler class onto the existing backlog`) to copy the stored class off your existing issues' `Handler:` lines onto labels; it is per-repository, re-running it is safe, and skipping it only means your pre-existing backlog drains unclassified (#1428)

- `/gaia-debt` now verifies that an issue still describes your code before it cuts a branch to fix it. An issue asserts a file path, a set of line citations, and sometimes a count its suggested fix is built around, and nothing re-checked any of those between the day it was filed and the day it is drained, so an issue whose subject was renamed, moved, or already fixed still read as actionable and would be implemented faithfully as a change the code does not need. Every subcommand now flags candidates whose cited file no longer exists, advisory only, since a renamed file does not by itself make a finding untrue. The full verification runs once, against the one issue about to be fixed, and it blocks: on a mismatch the fix is released back to the backlog and you are told what your tree says instead, rather than the issue being quietly rewritten or the fix proceeding on a re-derived guess, because choosing between correcting the issue and correcting the code is yours to make

- `/gaia-debt` now reads an issue's comments, for the issue it is about to fix. Posting a correction as a comment and leaving the body alone is the natural way to record that a suggested fix turned out to be wrong, and a body-only drain would rebuild work a comment already recorded as reverted, which is indistinguishable from ordinary progress once it is in the diff. A comment correcting part of the body now supersedes that part, newest first, and the substitution is stated before any code is written; a comment reporting the fix as already done, reverted, or unsafe stops the drain instead. The backlog listing stays body-only on purpose, so the cost is one extra read per issue actually being fixed rather than one per issue in your backlog

- a cross-remit out-of-scope finding waived at merge time, recorded in the pull request body rather than filed, now has to clear two disqualifiers on top of matching a path. A finding is no longer waivable when the change under review is what created the inconsistency it names, or when the change leaves a pointer in shipped content promising that a separate change will handle it; both kinds are filed as tech-debt issues instead. The path condition used to be sufficient on its own, which let a change wave away a defect it had just introduced in a file it happened to be touching.

- a rejected GAIA-Audit status POST no longer fails your audit job, on any of the four paths that can stamp one. Three of them let the rejection red the whole `code-review-audit` run, which told you your review had failed when it had passed and a transient GitHub API error had merely stopped a commit status from landing. The red also protected nothing: with no status posted the required check is absent and the merge button stays shut regardless, so it was noise on top of an already-closed gate. On the two skip paths it was worse than noise, because a failed step suppressed the very pull-request comment written to explain a shut gate, leaving the case most in need of an explanation with none. All four paths now log the rejection and publish it, and the comment names it, so you are told to re-run the workflow rather than sent to repair a `.gaia/VERSION` file that is fine, which is what the existing no-stamp message would have claimed. The comment covering the two audit-ran paths gained the rest of that reporting with it: a rejected POST is only one of five ways those paths can finish having stamped nothing, and the other four (an absent or empty `.gaia/VERSION`, a frontend digest that would not recompute, an audit not proven clean, a co-dispatched auditor CI cannot run) previously all read as "complete: no fixes needed" beside a shut gate. Advisory runs are unaffected, since a mode that posts no status by design earns no warning about not having posted one. The four disagreed because the answer was carried as a per-path argument rather than settled once; that argument is gone, so the answer cannot drift back one writer at a time. Nothing to do on your side: the argument was added and removed between releases, so no rendered workflow you received ever passed it (#1296)

- the pre-merge workflow no longer tells you a small correction costs a full audit round, and no longer sends you to defer one on that basis. It priced every re-dispatch at the 60-110k full-scope figure, but a member re-reads its whole owned surface only when it has no earned clearance to anchor on; otherwise it reviews just the delta since that clearance, which is what a comment or prose repair produces. Because the merge workflow is read before every merge, that one wrong number was quietly suppressing small correct edits across every pull request: each was individually judged not worth a cost the machinery was not actually charging. The page now prices a re-dispatch by the scope it resolves, names the specific conditions that do reset a review to full scope, and reverses the guidance for the cheap case, applying a one-line correction is the default for a member that still holds its clearance, and accepting-and-noting is reserved for the reset cases and for findings big enough to deserve their own change. It also prices the deferral side, previously treated as free, and adds a sweep for comment and prose repairs before a round's last dispatch so they ride a re-review already being paid for. This is the guidance-side counterpart to the reset-tier narrowing above. Maintainer-facing process guidance on a shipped wiki page, so it reaches adopters on their next `/update-gaia` (#1398)

- editing a coding-convention rule under `.claude/rules/` no longer makes every dispatched audit member re-read its entire owned surface. The whole directory was treated as one block governing the gate itself, so changing a word in a convention about how code should be written threw away each member's incremental review position and re-scoped the roster to a full pass. That made a rule edit the most expensive change in the repository, and the practical effect was that rule edits got deferred rather than made. Only the two rules that decide what the gate does with a review, the quality gate and the merge workflow, keep that reach; the rest are conventions. Nothing merges with less scrutiny: a convention change still requires a fresh review of the code under it, and what goes away is only the re-reading of work the change cannot have affected (#1397)

- the optional CI workflows GAIA renders for you now share their crons instead of each holding its own. GitHub bills every job a whole minute, so each tool that woke on its own schedule paid that minimum just to decide it had nothing to do, and on the private repositories most adopters run this on those minutes are billed. A new `gaia-ci.yml` is now the only scheduled workflow: it carries every distinct tool cron, and when one fires it asks each tool due on that cron whether it has work and runs only the ones that answer yes. It also skips a tool whose previous GAIA CI pull request is still open, which previously cost a full-history checkout and a billed minute to discover. Each tool workflow keeps its manual "Run workflow" button and behaves exactly as before, whether the scheduler starts it or you do. Two tools on the same schedule now cost one tick between them rather than one each: on the default schedules a quiet month goes from roughly 75 billed minutes to roughly 45, and if you had put all four tools on a daily cron, from roughly 120 to roughly 30. Tools on different schedules still cost a tick each on a day when both their crons fire, because GitHub starts one run per matching cron entry. **Action required:** run `/setup-gaia` after updating if you already have these workflows installed, it detects the drift and offers to re-render them; until then your installed copies keep their own crons (#1380)

- a scheduled `gaia-ci-*` workflow now decides whether it has work before it installs anything. All four ran a full checkout, a pnpm setup, a Node setup, and a frozen-lockfile install, and only then consulted the skip decision, so a tick that was going to do nothing still paid the entire setup to find that out. That is invisible on a public repository, where Actions minutes are free, and it is not free on the private repositories most adopters run this on, where minutes are billed. The decision now runs straight after checkout, against the `gh` CLI and the committed GAIA binary, neither of which needs an install, and pnpm, Node, and the install are gated behind it. Every skipped tick does less work and finishes sooner; because a job is billed in whole minutes, that converts to a billed minute recovered only where the old setup pushed the job past sixty seconds, which is plausible on the 2-core runners private repositories get and is unmeasured. The floor of one billed minute per tick is set by the rounding and by how many crons there are, so this change cannot go below it. A tick that does run behaves exactly as before. The `gaia-ci-*` workflows are re-rendered by `/setup-gaia` rather than refreshed by `/update-gaia`, so this reaches an adopter's CI on their next `/setup-gaia` (#1312)

- GAIA's own bats suites are now split across shards by file size rather than by file count, which takes a hand run of the whole set from about 227 seconds to about 202. ## [1.0.0] - 2026-04-30

### Initial release

GAIA v1.0.0 is the inaugural public release of the GAIA React workflow, a Claude-native foundation that ships skills, commands, hooks, a wiki, and a curated React Router 7 app skeleton designed for agentic development from day one.

#### Highlights

- **Claude integration surface.** `.claude/` ships with rules, settings, hooks, an agent skills bundle (`typescript`, `react-code`, `tailwind`, `tdd`, `skeleton-loaders`, `playwright-cli`, `eslint-fixes`, `update-deps`, scaffolders), and an agent commands catalog. `CLAUDE.md` is curated for context economy.
- **GAIA workflows.** `/gaia plan`, `/gaia handoff`, `/gaia pickup`, `/gaia audit` cover task orchestration, session continuity, and knowledge-store hygiene. `/gaia-init` bootstraps new projects from the template.
- **Wiki vault.** Architecture overview, decisions (Quality Gate, pnpm, Dark Mode Modernization, etc.), modules (Routing, Styling, i18n, Form Components), concepts (Agentic Design, API Service Pattern, Component Testing, Task Orchestration), and a hot/log pair for session continuity.
- **App stack.** React Router 7, React 19, Tailwind v4, ESLint 9, Vite 8, Vitest 4, TypeScript 6, pnpm 10, MSW 2 + `@msw/data` 1.x.
- **Form system.** Conform + Zod for type-safe forms with reusable field components.
- **i18n.** `remix-i18next` middleware, English + Japanese language scaffolding, `LanguageSelect` component, Storybook locale switcher.
- **Dark mode.** Cookie-as-truth + `@epic-web/client-hints` + optimistic `useFetchers()` UI.
- **Quality gate.** Mandatory pre-commit pipeline: simplify, localization check, typecheck, lint, unit tests, E2E tests, dev smoke test, build. Zero warnings tolerated.
- **Release tooling.** Tag-triggered `release.yml` builds a scrubbed tarball; `create-gaia` bootstrapper consumes it via `npx create-gaia@latest my-app`.
