# Code Audit Team

The pre-merge gate is a **config-driven roster of auditor members**, not a single agent. `.gaia/audit-ci.yml`'s `auditors:` block maps file globs to specialized auditor members; a diff can dispatch more than one member, and the shared `GAIA-Audit` gate requires every dispatched member's own clearance before a merge unblocks. [[Code Review Audit Agent]] (`code-audit-frontend`) is the roster's default, adopter-facing member; this page covers the roster mechanism itself and the maintainer-only members layered on top of it.

## Roster shape

Each `auditors:` entry carries a `name`, a `globs` list, an `audience` (`adopter` or `maintainer`), a `push_fixes` flag, and, on exactly one entry, `default: true`. Every member, the default included, declares its own domain in `globs`; there is no implicit domain inferred from anywhere else. Ownership resolves in two precedence tiers: every **claimant** member's (a member without `default: true`) globs are matched first, first-match-wins over roster order, so roster order among claimants is load-bearing; only once every claimant has failed to match does the **default** member's own globs apply, as a catch-all second tier. `audience: maintainer` entries sit inside `# gaia:maintainer-only` marker comments; the release scrub strips them from the shipped config, so an adopter clone's built-in fallback roster carries only the adopter-audience members below.

| Member | Globs | Audience | `push_fixes` |
| --- | --- | --- | --- |
| `code-audit-frontend` (default) | `app/**`, `test/**`, `.storybook/**`, `.github/workflows/**`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `tsconfig*.json`, `*.config.ts`, `*.config.mts`, `*.config.mjs`, `*.config.cjs`, `*.config.js` | adopter | `true` |
| `code-audit-github-workflows` | `.github/workflows/*.yml`, `.github/workflows/*.yaml`, `.github/actions/**/*.yml`, `.github/actions/**/*.yaml` | adopter | `false` |

The default's `.github/workflows/**` glob and the workflows member's `.github/workflows/*.yml`/`*.yaml` globs overlap textually, but the two-tier precedence resolves it: the workflows member is a claimant, so a `.yml`/`.yaml` workflow file matches it first; in practice every file under `.github/workflows/` is itself a `.yml`/`.yaml` workflow, so the more specific claimant glob always wins there. The default still declares the broader glob so its stated domain matches what it used to implicitly cover, even though the claimant's narrower glob wins in practice.

The files under `.gaia/cli/templates/workflows/`, partials included, are deliberately ownerless: a script pins them byte-identical to their source (the CLI's own bundling step), so a reviewer of the copy would decide nothing a reviewer of the source template has not already decided. Finding no owner for that directory is the designed state, not a gap to fix.

## Ownership classifier

Roster parsing and per-path ownership live in one shared, sourced module, `.claude/hooks/lib/audit-scope.sh`, that every dispatch resolver and the merge gate itself consult, rather than each parsing the roster on its own. It parses the roster (`.gaia/audit-ci.yml`'s `auditors:` block when present and non-empty, else the same built-in default roster, itself marker-wrapped for the maintainer-only entries) exactly once per run, and answers three separately-named questions that are never interchangeable: which paths the merge gate's out-of-scope allowlist covers, an ordered three-way classification for the `/update-gaia` self-mod bypass (out-of-scope / the audit workflow itself / in-scope), and which member, if any, owns a given path, resolved in the two precedence tiers above (every claimant's glob first, first-match-wins over roster order, then the default member's own declared globs, otherwise ownerless). Conflating any two of those questions is a merge-gate bypass, which is why they stay three distinct predicates in the one module instead of one generalized check.

The out-of-scope allowlist admits `wiki/`, `.claude/`, `.specify/`, `.gaia/`, `docs/` and root-level `*.md`, and nothing else at the root. `public/**` is deliberately not on it, since the tree carries executable JavaScript (a service-worker registration) under that prefix, so it stays in scope, owned by the default member's catch-all. One predicate serves two consumers, the merge gate's legacy fallback branch and the default member's digest fold, so widening the allowlist has to move both together or a merge deadlocks: a path allowlisted in one but not the other resolves an empty dispatched set in one place and a nonzero one in the other.

### Base provenance: telling unresolvable apart from genuinely empty

A shared library under the hooks library directory (`.claude/hooks/lib/audit-base-provenance.sh`) resolves the diff base for a diff and reports a **trust token** and an **anchor token** alongside it. The merge gate and the member resolver both read that one resolver; neither owns a copy of the rule, which is what keeps the two from disagreeing about **whether a given provenance is decisive**. That claim is scoped to the predicate exactly that way: the gate additionally binds its own relaxation to the pull-request record (anchor `pr-record`, local HEAD at the pull request's recorded head sha, and the gated command naming that same pull request), so the two can still reach different verdicts about a given *merge*, with the gate always the stricter of the two.

The trust token answers one question: is an empty base-to-HEAD range decisive, meaning it holds no audit obligation on its own?

| Trust | How it resolves | Decisive on empty? |
| --- | --- | --- |
| `remote` | A merge base against a fully-qualified `refs/remotes/origin/<branch>` ref | Yes |
| `supplied` | The caller passed a base and it verified in this checkout | Yes |
| `local` | A merge base against a bare local branch name, because no remote-tracking ref existed | No |
| `unresolvable` | Nothing resolved | No |

The fully-qualified spelling is load-bearing rather than pedantic. Git resolves the bare revspec `origin/<name>` through `refs/heads/` before `refs/remotes/`, so a local branch literally named `origin/main` supplies the base while `refs/remotes/origin/main` still verifies, and the ambiguity warning goes to a stderr every call site discards. Such a branch is reachable without insider action, because checking out a pull request names the local branch after the author-chosen head ref.

The predicate has two conjuncts: the diff command exited zero, **and** the trust token is `remote` or `supplied`. A failed diff is never an empty diff, and capturing git's exit status alone is necessary and not sufficient, since a local default branch that has already absorbed a branch's commits puts the merge base at HEAD, making the range empty for a pull request that changes plenty.

The anchor token answers a different question, which branch the base was actually taken against: the repository default or the pull request's own recorded base. It exists for diagnostics and because the merge gate legitimately runs two derivations in one pass; the trust predicate never consults it. A `pr-record` anchor always carries `remote` trust, because every site that prefers the record verifies its remote-tracking ref first.

What each consumer does with the trust-keyed rule:

- The merge gate mirrors the empty-range half at its out-of-scope bypass, under a stricter conjunction: the anchor must be `pr-record`, local HEAD must equal the pull request's recorded head sha, and the `gh pr merge` being gated must name that same pull request. The last conjunct is what makes the other two mean what they say: the record is read for the CURRENT BRANCH, so without it the relaxation proves the checkout sits on *a* pull request rather than on the one being merged. The gate reads the merge's own reference through the shared command scanner in `.claude/hooks/lib/repo-scope.sh`, never a second parser of its own, and confirms a bare number against the record's. Every abstention denies, so what the conjunct proves is bounded to the shapes that scanner reads exactly: the merge is the first command in the tool call, it carries no flag shape the scanner declines to model, no separator or comment puts a second command beside it, which the scanner reports from the same tokenizing pass that read the reference, and every byte of the command is in the small set a merge invocation needs. That last clause is a separate guard rather than part of the scan, and it is an allowlist rather than a list of dangerous spellings: an expansion is ordinary word text to a tokenizer that models words, so a merge carrying one reaches the end of the scan with no separator found while the shell runs the payload first, and which text runs a command is a property of the shell and its version rather than a fixed set of sequences. Two attempts to enumerate that set were both incomplete. A branch name and a URL deny too, since resolving either to a number needs a second network read. Reusing that scanner is what closes the shape a hand-rolled one gets wrong: `gh pr merge` has six value-taking flags, and skipping options by their leading dash alone reads a separated value as the positional, so a flag carrying the record's own number would clear a merge of an entirely different pull request. Every other shape denies. The permit stays a silent zero exit; the provenance reason travels on stderr as a diagnostic line, because the gate has no allow-with-reason channel and giving it one would short-circuit the permission system for `gh pr merge`.
- The gate's self-modification bypass is deliberately not relaxed on emptiness. It is reachable from the member-aware path and would clear every dispatched member at once, across mismatched anchors, since the member set comes from a default-branch-anchored derivation while its own range comes from the record-anchored one.
- The member resolver adopts the shared resolver and changes no answer: an unresolvable base and an empty range both still yield an empty member set, because its callers hold the provenance and decide there.

The residue is worth stating rather than hiding. A pre-merge dispatch resolution predicts the gate but cannot see the pull request's recorded base, because it must stay offline-safe. A zero-commit branch whose pull request targets a non-default branch can have the resolver answer that nobody is owed while the gate's own range is non-empty. The gate denies, so the resolver's answer merges nothing, and the deny is thin: on that path the gate's member set is empty by construction, so it falls through to its legacy single-signal branch, whose reason lists the clearance signals it did not find and names no member set at all. That branch also clears on a frontend signal alone, so a specialized member the record-anchored range would owe is not demanded there. No recovery mechanism exists for that shape.

The shared resolver, `audit_resolve_base_provenance`, is the one definition tree-wide; every named consumer calls it rather than deriving base provenance itself. The worthiness presence gate is a consumer despite failing open: two merge gates scoping different changed sets on one head must not drift silently apart. The existing base-derivation check is not extended for this; it is scoped to the member agent files and governs review bases, a different concern.

See [[PR Merge Workflow]] for the gate's own signal table and bypass rows.

A sibling module, `.claude/hooks/lib/audit-machinery.sh`, holds the one list of **audit-machinery paths**: every file whose bytes can change what a member reviews, who reviews it, where a clearance lands, or whether a clearance is believed (the roster, the classifier and machinery modules themselves, the clearance writer and reader, the merge gate, the CI workflow and its bundled templates, the agent definitions, among others). A `.bats` suite under a machinery `/**` prefix counts as machinery like any other file under it; the roster's own `.bats` globs (see below) separately dispatch a real member to review the suites themselves.

Every member's clearance marker is keyed to a **content digest**, not the whole repository tree: a sha256 over exactly the files that member owns plus this machinery set (plus the in-scope-but-ownerless paths, for the default member; see [[PR Merge Workflow#Marker key]]). The machinery set is what makes a machinery edit rotate **every** member's digest, since it sits in every member's input set by construction, and because the classifier and machinery modules are themselves machinery, a classifier edit rotates every digest too. Machinery-list completeness is therefore load-bearing, not cosmetic: an unlisted gate-machinery file would rotate no member's key, a fail-open. A fixture in the machinery library's own test suite asserts every gate-machinery file (the trailer/status producers, the CI parsers, the dispatch resolvers, the noop detector, the disposition gate, among others) is matched by `audit_path_is_machinery`.

The digest functions in `.claude/hooks/lib/audit-digest.sh` (`audit_digests_all`, `audit_member_digest`) take an optional ref argument, defaulting to `HEAD`; production callers pass a base sha through it to derive a prior digest at an incremental base rather than only at HEAD. The constraint that this machinery never resolves a main or tree root, and answers what key a tree writes under rather than where anything is, belongs to `.gaia/scripts/audit-key-lib.sh`, a property of that file, not of the digest lib. That the digest functions accept a ref proves the lib can hash a different tree; it does not mean the lib can scope to a diff between two trees, which would be a new capability, not a parameter already present.

### Dirty-scope refusal

A clearance marker's content digest is computed over `git ls-tree HEAD`, while a member reviews a file by Reading it, which returns working-tree bytes. On a dirty tree those disagree, so a pass could otherwise write a marker certifying content nobody read. Each gating member checks `git status` (NUL-delimited, so it is correct on paths carrying quotes, control bytes, or non-ASCII) over its own resolved review-scope list immediately after resolving it, and refuses the pass when that list is dirty: no clearance marker is written, a findings sidecar names each dirty path, and the operator re-dispatches once the path is committed or reverted. The check runs ahead of any self-heal a member's own remit performs, so a sibling member's legitimate write to files outside this member's scope cannot trip its refusal, and a status the guard cannot determine fails closed (refuses) rather than reading as a clean tree. The advisory-only prose-legibility member used to be the one exemption to this; it is deleted (harness triage P3-09), and every current member gates.

### Scratch space for on-disk evidence

The clean-tree invariant above composes with a second fact into an obligation neither states alone: establishing that a guard is not hollow means breaking the construct the guard names and watching its check go red, which needs real bytes on disk. The mutation therefore has to happen on a copy, and the only writable space a dispatched subagent is handed is the session scratchpad, which every member of one parallel wave shares. A member improvising a name there picks the name its siblings also pick, and one member's copy lands over another's. Neither direction of that overwrite announces itself: a pristine tree over a mutated one makes the mutation look like it did not red, which reads as a hollow assertion that is not there; a mutated tree over a pristine one reds a check that has nothing to do with the change under review.

Each member's definition instructs it to name its own scratch paths (mutation trees) with its own member name, so co-dispatched members never collide.

## Dispatch resolver

`.gaia/scripts/resolve-audit-members.sh` turns the current branch's diff into the **dispatched member set**: the deduped, lexically-sorted list of member names owning at least one changed file. It resolves each changed path's owner through the shared ownership classifier above and collects the unique, non-empty owners; empty stdout means the whole diff is out of audit scope. It is generic over the roster: a new member is a config entry plus an agent file, no resolver edit.

## Spawning: the same set, resolved ahead of the gate

The gates are reactive: they deny, they never spawn. The pre-merge procedure resolves the member set directly with `.gaia/scripts/resolve-audit-members.sh` and spawns exactly those members instead of guessing one, fail-closed: an empty result spawns the default member, mirroring the merge gate's own legacy fallback (which still requires the default member's clearance there), and an in-scope path owned by nobody owes the default member too, since its digest folds that path in (see [[#Ownership classifier]]). When the resolver names specialists, the gate checks only those, so spawning the default member is that path's only coverage. The spawn set is a superset of what the gate can require, so no diff exists where the gate demands a marker nothing was spawned to produce.

A claimant member with nothing to audit is never spawned, and if a stale caller spawns it anyway, it self-skips (its agent file carries the skip clause). The default member carries no self-skip: spawned, it runs a full review.

### Clearance digest keying

**The clearance digest stays keyed to tree content.** Keying the marker to the reviewed diff instead of the whole owned content is declined on measurement, not rejected on principle: every member already resolves a per-member base and the writer already accepts it as `--base`, so the input a diff-keyed digest would need is in hand and this is not a feasibility call. What the measurement says is that the failure the re-key repairs is too rare to pay for the surface it moves.

The figures below were measured once, over a 32-day window of recorded member dispatches (first record 2026-08-02T01:18:32Z, last 2026-09-02T03:19:13Z), and cannot be re-derived. A bats suite appended real rows by running the real dispatch resolver against a real checkout, so the pair count includes test-generated observations; the contamination is stated here rather than silently corrected for.

```text
window_days                   32
since                         2026-08-01T03:20:16Z
records                       2406
transitions                   1965
exposed_pairs                 626
lost_clearances               57
peer_merge_respawns           3
own_change_respawns           54
peer_merge_rotations_upper    20
```

Read against its denominator: 626 pairs were exposed to the failure at all, 57 of them lost a clearance, and 3 of those 57 are attributable to a peer's merge landing under an already-audited branch rather than to the branch's own edits. The remaining 54 are the branch's own content changing, which is the digest working as designed. Three peer-merge re-spawns across a month of real traffic is the rate the re-key would buy down, against the following surface.

- **Production consumers of the digest: seven.** The selection rule is files calling `audit_digests_all` or `audit_member_digest`, tests excluded. `git grep -ln 'audit_digests_all\|audit_member_digest' -- . ':!*tests*' ':!*.bats'` returns eight paths: `.claude/hooks/audit-stamp-trailer.sh`, `.claude/hooks/lib/audit-digest.sh`, `.claude/hooks/post-audit-status.sh`, `.claude/hooks/pr-merge-audit-check.sh`, `.gaia/scripts/audit-member-digest.sh`, `.gaia/scripts/audit-scope-digest.sh`, `.gaia/scripts/audit-write-clearance.sh`, and this page, which names the functions in prose and calls neither.
- **Prose sites restating the ls-tree recipe: eight.** The selection rule is pages that restate the recipe, not pages that merely reference a digest, so `git grep -ln 'ls-tree' -- wiki .claude/agents` is a candidate list a human triages. It returns nine files; the eight that restate it are the five `.claude/agents/code-audit-*.md` definitions, `wiki/concepts/Code Review Audit Agent.md`, `wiki/concepts/PR Merge Workflow.md`, and this page. `wiki/concepts/Audit Disposition and Debt Fix.md` is the ninth and is not one: it names a failing `git ls-tree` only as a fail-closed condition.
- **Bats suites touching the digest surface: thirteen**, under the rule "suites whose assertions would need rewriting on a recipe change". `git grep -ln 'audit_member_digest\|audit_digests_all\|gaia-audit-digest-v1' -- '*.bats'`. Two of the thirteen are pinned to tree-content keying specifically rather than to the digest as an opaque value: `.gaia/tests/hooks/audit-digest-lib.bats`, whose per-class byte-flip rotation cases, ls-tree failure arm, and path-encoding cases all read the recipe directly, and `.gaia/scripts/tests/audit-base-agreement.bats`, whose probe that a member's changed-file list is HEAD's content has tree-content keying as its entire warrant.
- **The cascade.** `.claude/hooks/lib/audit-digest.sh` sits under the `.claude/hooks/lib/**` machinery prefix, so a recipe change is a full five-member cascade: every roster member's digest rotates at once and every member's incremental review base resets to full scope.
- **The orphaning.** Existing markers become inert files nobody looks for, rather than artifacts something rejects. Existing trailers and commit statuses fail a byte comparison against the recomputed digest. The merge gate denies with its ordinary generic clearance-missing reason, which names nothing about a recipe. There is no `digest_recipe_version` field, no migration path, and no grace window anywhere.

Orphaned and rotated are two different claims, and conflating them prices this surface wrong. Only a change to the digest recipe, the `gaia-audit-digest-v1` sentinel, `AUDIT_MACHINERY_PATHS`, or the roster moves the key space, and only then does an existing marker, trailer, or status become unfindable. Any edit to a machinery path rotates every member's digest once, exactly as any machinery change does, and re-dispatches every member in flight at that commit. A rotation is ordinary and self-healing; an orphaning is neither. The scope digest a member captures and the staleness check the clearance writer runs against it are both on the rotating side of that line: they read the recipe and never define it.

## AND-aggregation at the merge gate

The local merge deny-hook (`.claude/hooks/pr-merge-audit-check.sh`) resolves the dispatched member set, computes every roster member's own content digest in one walk, and requires **every** dispatched member cleared before allowing `gh pr merge`:

- `code-audit-frontend` clears via any of its existing signals (local `<digest>.ok` marker, `GAIA-Audit` commit trailer, GitHub CI status, `chore(deps)` bypass, or the self-mod-only GAIA-update bypass), each checked against its own current content digest.
- A specialized member clears via its own marker, `.gaia/local/audit/<digest>.<member>.ok` (local/advisory-only, no CI or trailer equivalent), or the same self-mod-only GAIA-update bypass `code-audit-frontend` uses. That bypass proves a property of the PR (the sole in-scope change is a verbatim re-render of the bundled audit-workflow template), not a property of one member, so it is resolved once per run and clears **any** dispatched member with no earned marker of its own. Markers key to each member's own content digest, not a shared tree, so members are naturally order-independent: an out-of-glob change rotates no digest, and the trailer stamp the last member to clear lands rotates no member's digest either, whether that lands as an empty commit (leaving every blob byte-identical, on an un-pushed or detached HEAD) or as no commit at all (on an already-pushed attached HEAD). A live refusal for a member's current digest is checked first and stays absolute, overriding the bypass either way. See [[PR Merge Workflow]], Marker key.

A live **refusal** for a member's current digest (`.gaia/local/audit/<digest>[.<member>].refused`) is checked before that member's earned marker and is absolute: it denies the merge regardless of a same-digest earned marker. There is no minting step and no carry-forward clearance machinery, a member not already cleared for its own current digest simply has to be re-dispatched; the digest key is what shrinks how often that happens, since an unrelated or out-of-glob change never rotates it in the first place.

A zero-match dispatch (the resolver finds nothing, or is absent/unusable) falls through to the **legacy single-signal gate**, evaluated for `code-audit-frontend` alone. This is a fail-closed fallback, not an auto-allow: the legacy gate's own out-of-scope bypass still denies an ownerless-but-in-scope file (e.g. `public/logo.svg`) with no marker, because such a path folds into the default member's own digest input set (see [[PR Merge Workflow#Marker key]]).

`.claude/hooks/post-audit-status.sh` POSTs the `GAIA-Audit` commit status and mirrors the same aggregation: handed an earned marker it posts success only once every dispatched member is cleared and none of them holds a live refusal for its own current digest, declining with `members pending <list>` otherwise. The orchestrator is the one that calls it, once, after every dispatched member holds its own earned marker and every finding from every round is fixed or recorded, never a member's own agent (see [[PR Merge Workflow#Posting the status last]]). The trailer stamp lands earlier and separately, by whichever dispatched member clears last in its own handshake; when the stamp created a commit (un-pushed or detached HEAD), that member pushes it as part of the same handshake, so the status the orchestrator posts afterward goes on the sha the PR head actually carries. The hook requires local HEAD to be the pushed head and declines `stamp not pushed` rather than greening a sha the stamp is about to replace. On an already-pushed attached HEAD the stamp makes no commit at all, local HEAD already is the pushed head, and the orchestrator's status posts immediately. A success description is always the fixed three-field `<version> <frontend-digest> <tree>` shape; there is no carried variant. Handed a **refusal** instead, the same hook posts `state=failure` immediately, from the clearance writer at the moment it records the refusal, skips the member-aware gate (the refusal is that member's answer, so waiting for the roster to clear would wait on the condition it contradicts), and writes a two-field `refused by <member> <digest>` description that deliberately carries neither the cleared shape nor a version in its first field. That arm is what gives refusal precedence a server-side signal, since GitHub's auto-merge completes on the required status alone and never runs the merge hook; see [[PR Merge Workflow]], Signals.

## Maintainer-only members

Two members carry `audience: maintainer`: `code-audit-maintainer-shell` and `code-audit-maintainer-node`. What each one owns is enumerated in `.gaia/audit-ci.yml`, which is the single enumeration and the one the dispatch resolver reads; this page describes each member's subject and the reasoning behind the boundaries rather than restating the globs.

A third maintainer-only member, `code-audit-maintainer-prose`, reviewed GAIA's own instruction prose for gratuitous complexity and fed a `prose/*` recurrence signal into the [[Policy-Memory Loop]]; it was deleted as advisory-only and never gate-affecting (harness triage P3-09). Its former territory -- skills, slash commands, instruction runbooks, the Code Audit Team's own review lenses, the CLI health lenses, the forensics prompts, and the spec-kit extension's commands, rules and templates -- is declared `unowned:` in `.gaia/audit-ci.yml` rather than reassigned; nothing replaced its lens.

`code-audit-maintainer-shell` and `code-audit-maintainer-node` review framework source the frontend and workflows auditors never scope. The shell member's subject is the framework bash GAIA ships and runs, the bats suites guarding it, the git hooks under `.husky/`, and the declarative machinery deciding what ships, what executes, and whose clearance is believed; the two sections below give the reasoning for the bats suites and for that declarative half. Its lens is a hook-contract read, a bats-suite read, `shellcheck` as a deterministic oracle, and bash 3.2 / BSD-vs-GNU portability review. The husky hooks are claimed by a bare directory glob rather than an extension one because they carry no extension and no shebang: husky runs them as `sh -e`, so they are POSIX `sh` rather than bash, and the oracle reads them as `shellcheck -s sh`. They are the only surface in this member's remit that is not audit machinery, claimed because `.husky/pre-commit` is the Quality Gate floor for every commit, not because its bytes change what a member reviews.

`code-audit-maintainer-node`'s subject is the CLI's own TypeScript: the sources under `.gaia/cli/src/`, the render templates, snapshots and placeholders beside them, the build and config surface that decides what the CLI's test and lint runs execute, and the standalone `.mjs` executables under `.gaia/scripts/`. Its lens is correctness, error handling, filesystem/IO safety, Zod schema fitness, and shell/`gh` injection safety. Two of its roster entries carry reasoning a glob alone does not show. `.gaia/cli/pnpm-workspace.yaml` is claimed by an exact path because the default member's own `pnpm-workspace.yaml` glob never crosses a `/`: it matches the repository-root file and reaches the CLI workspace's copy not at all, so without that entry the workspace's supply-chain policy (`minimumReleaseAge`, `trustPolicy`, and both exclusion lists) resolves an empty dispatched set and merges with no member responsible for it. The CLI's own tool configs (`vitest.config.ts`, `eslint.config.mjs`, `prettier.config.mjs`) are directory-anchored for the same reason, and their extension family is enumerated one entry per extension rather than written as a single `.gaia/cli/*.config.*` glob, because `*` matches any run inside a segment, so the one-glob form also spells `.gaia/cli/<name>.config.sh`, which `code-audit-maintainer-shell` already claims: an overlap as glob languages, not merely against files that exist today. The dialect has no way to subtract an extension, so the enumeration is forced; what keeps it exhaustive is the coverage invariant, which reports a config extension no roster entry names as ownerless rather than letting it merge unreviewed. `vitest.config.ts` is the sharpest of the three, since its `setupFiles` executes arbitrary code in every CLI test run. Qualifying the source entries by extension is narrower than a bare `.gaia/cli/src/**` glob would be, deliberately: a file under an extension no entry names reaches no member, a named, accepted cost.

Both maintainer members are advisory-only, no self-heal, and carry `push_fixes: false`: a maintainer member never pushes a fix commit, it reviews and reports; the one commit it does push is the content-preserving trailer stamp, on the round where it is the last member to clear. Both are release-excluded (their agent files, roster entries, and glob references are marker-wrapped and stripped from the adopter bundle), so an adopter clone's Code Audit Team never dispatches them.

### The bats suites are owned, deliberately

`code-audit-maintainer-shell` also owns the `.bats` suites guarding that bash (`.gaia/**/*.bats`, `.github/**/*.bats`), which together cover every bats tree in the repo: `.gaia/scripts/tests/`, `.gaia/tests/{forensics,hooks,lib,sandbox,statusline}/`, `.github/audit/tests/`, and `.github/forensics/tests/`.

Ownership is the deliberate choice because a `.bats` file is not a `.sh` file: without a bats glob, a diff touching only test suites matches no member's globs, dispatches an empty member set, and rides the merge gate's out-of-scope bypass. Those suites are the only enforcement standing behind the framework's shell, so a commit that weakens, skips, or deletes one is simultaneously the change least affordable to merge unreviewed and the one that most easily escapes review. The shell member is the natural owner: bats suites are bash, `shellcheck` parses them as bash and reports genuine defects in them, and the reviewer who knows the script knows what its suite is supposed to prove. The agent carries a bats-specific lens for the failure modes a suite's own green run cannot catch: assertions that structurally cannot fail (per `.claude/rules/bats-assertions.md`), a silently loosened or deleted assertion, and a `skip` that retires coverage.

A bats-only diff therefore dispatches `code-audit-maintainer-shell` and requires its clearance, the same as any other change to the framework's shell.

### The declarative half of the machinery is owned too

`code-audit-maintainer-shell` also owns the roster itself and the release scrub's config (`.gaia/*.yml`, which generalizes the bare `.gaia/audit-ci.yml`), the manifest that decides what ships plus the state and hook-scope registries and their schemas (`.gaia/*.json`), the release exclusion list (`.gaia/release-exclude`), the version literal the clearance writer stamps into every marker (`.gaia/VERSION`), the hook registrations (`.claude/settings.json`), the review-ownership file (`.github/CODEOWNERS`), the model-pricing table the bash cost tooling reads (`.gaia/scripts/token-rates.json`), the rules directory (`.claude/rules/**`), and the `code-audit-*` agent definitions that produce clearances. Every one of those is an audit-machinery path (see [[#Ownership classifier]] above): a commit that rewrites the roster, an agent definition, or the version literal changes what a member reviews, who reviews it, or whether a clearance is believed, exactly the surface this member already gates, so without these globs such a commit matched no member and merged unaudited. The application-scope default member has no remit over shell or roster config, the workflows member's remit stays the live workflow and action YAML, and the CLI-TypeScript member's remit stays `.gaia/cli/src/**`'s enumerated extensions plus its build/config surface (`package.json`, `pnpm-lock.yaml`, `tsconfig*.json`), so the shell member is the fit for the rest. This fills the unowned corner of the machinery set that is meant to have an owner, everything except the pinned build-artifact templates under `.gaia/cli/templates/workflows/`, which stay deliberately ownerless (see Roster shape above).

### Reset-predicate tiers for the per-member incremental review base

A per-member incremental review resolves its base against a **reset-predicate partition** over three tiers, computed by `.claude/hooks/lib/audit-rules-changed.sh`: **global** (a changed path resets every dispatched member's anchor to full scope), **member** (matches only a member's own `.claude/agents/<name>.md`, resetting that member alone), and **merely-shared** (every other machinery path, the ordinary tier for a hook library or rule file more than one member's clearance depends on but that is not itself gate-critical; it resets no anchor). A fixture in that library's own test suite asserts every global path is also machinery.

The generating rule for GLOBAL is scope and belief, never criteria: which paths a member owns, how its digest is computed, whether a clearance is believed. A coding-convention rule under `.claude/rules/**` changes how code should be written, not any of that, and an anchor records that a member already READ a surface, which a reworded convention does not un-read; what the convention change owes is a fresh clearance for the diff under review, already required because `.claude/rules/**` sits in `AUDIT_MACHINERY_PATHS`. GLOBAL therefore keeps only `quality-gate.md` and `pr-merge.md`, the two rules that decide gate mechanics; every other rule file is merely-shared.

Adding a `.sh` under `.claude/hooks/**` needs to reach `.gaia/local` only through a resolved root, never a bare literal (`bash .gaia/scripts/check-hook-scope-manifest.sh` scans every hook for the violation), and a file under `.claude/hooks/lib/**` is merely-shared unless it is added to the global tier above. `.claude/rules/maintainers/hook-registration.md`, path-scoped to `.claude/hooks/**/*.sh`, names both at edit time.

## Deterministic roster check

`.gaia/scripts/verify-audit-roster.sh` asserts a named set of invariants over the roster and ships to every clone (manifest class `owned`: a roster change reaches adopters through `/update-gaia`, so they need the check as much as the maintainer does). Its repair, `.gaia/scripts/write-audit-remits.sh`, ships alongside it in the same class, so an adopter who tunes the default member's globs is one command from green rather than hand-transcribing a region. The script's own header is the source of truth for the invariant list and the bounded, decidable glob dialect it classifies against; this page does not restate either.

Two per-member properties -- every roster member's agent file registered in `AUDIT_MACHINERY_PATHS` (`.claude/hooks/lib/audit-machinery.sh`), and every member's `name` carrying the `code-audit-` prefix the local self-heal repair boundary (`.claude/hooks/block-selfheal-paths.sh`) binds a dispatched member to -- are real-tree assertions in the check's own bats suite rather than a runtime invariant of the script, because both hold over the committed roster whether or not a fixture roster is under test.

Named limits, not defects: the check verifies coverage over *paths*, never over *globs*, so a claimant glob narrow enough to reach no file is invisible to it as a glob, and surfaces only through whatever tracked paths it leaves ownerless; it verifies *region parity*, never the truthfulness of the prose around a region. Repairing rotates every member's clearance, because the agent definitions the writer edits are audit-machinery paths, so running the repair invalidates every marker on a pull request and forces a full re-dispatch, which is why the repair is the orchestrator's to run before dispatch or between rounds, never mid-audit and never by a dispatched member -- `.claude/hooks/block-selfheal-paths.sh` denies a dispatched member the invocation outright.

Two limits are new with this change: a hand-edited **sentence** inside a region passes the check, since the glob bullets are policed and the sentence that consumes them is not, and re-running the writer is what restores it; and moving `default: true` between roster members changes which sentence each affected member owes while changing no glob, so the check stays green on two now-wrong regions until the writer runs again. Both are named limits in the same voice as "verifies region parity, never the prose around a region", not defects to close here: carrying the sentence templates inside the check would mint the second hand-synced copy this change exists to delete.

Neither the check nor its writer is wired into CI or a hook automatically: nothing gates a merge on either, so both are run by hand after a roster change (`bash .gaia/scripts/verify-audit-roster.sh`, then `bash .gaia/scripts/write-audit-remits.sh` to repair).

## Ruleset-aware required-check confirmation

`read-audit-ci-config.sh`'s `required_check_confirmed` helper (used by the per-author local/CI resolution) confirms the `GAIA-Audit` required check under either branch-protection model: classic branch protection (`required_status_checks` context, tried first, the only path an adopter repo with classic protection ever needs) or a repository ruleset (`GET repos/{owner}/{repo}/rules/branches/<branch>`). The ruleset read ships to every clone, adopter and maintainer alike, so a repository protected by a ruleset rather than classic branch protection confirms correctly too; a repo protected by classic branch protection alone never reaches the ruleset read. The confirmation is advisory only: whichever model confirms, or neither does, the resolved mode never changes.
