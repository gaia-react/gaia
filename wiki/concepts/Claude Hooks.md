# Claude Hooks

Bash scripts that run on Claude Code tool calls. Configured in `.claude/settings.json` under `hooks.PreToolUse` (and other event types). Hook scripts filter by command content internally. Advisory hooks that act on only a few verbs also carry an `if:` filter (one permission rule per handler) in their settings registration, so they never spawn on other calls. Deny guards never use `if:`: the filter is best-effort, and their verb arming must stay fail-closed. A Claude Code version that ignores `if:` runs the hook on every call, which fails safe because each hook still filters internally.

Exit code semantics:

- `exit 0`: pass; stderr is shown to Claude as advisory
- `exit 2`: block; stderr is shown to Claude as the reason
- JSON `permissionDecision: "deny"` on stdout: block via the structured API; the reason string is surfaced to Claude
- JSON `permissionDecision: "ask"` on stdout: rule neither way, put the call to the operator; the reason string is what they answer on. Reach for it where the property separating a wanted call from an unwanted one is the operator's intent, which no hook reads. `block-eslint-config-edit.sh` is the one bundled hook that does

**One decision per tool call, and it covers the whole call.** A `PreToolUse` hook receives `tool_input.command` as a single string and returns one allow/deny verdict for the entire invocation, before any of it reaches the shell. There is no per-line or per-clause execution: a Bash call chaining `a && b && c` is adjudicated once, so a hook that denies `c` drops `a` and `b` with it. Nothing runs, and the deny reason names only the clause that tripped the guard, so the dropped siblings are invisible unless their effect is checked directly.

The consequence is a rule about how commands are composed, not just about hooks: **never chain a command whose failure you would not notice onto one a guard might deny.** Filing a GitHub issue and then deleting its body file is the canonical case, and `.claude/skills/file-tech-debt/SKILL.md` mandates two separate tool calls for exactly this reason: a denied cleanup that shares an invocation with `gh issue create` costs the filing, silently. The property is general to every `PreToolUse` guard, so treat any compound Bash call that crosses a guard's subject matter the same way.

## Bundled hooks

Hooks are grouped by the safeguard they enforce, not by event type. The index below is the scannable view of the same set: one row per hook script at the root of `.claude/hooks/`, answering what fires it and what it is for. The subsections after it carry the reasoning, the payload shapes, and the failure modes, which is what a reader needs once the index has pointed them at a name.

**Event or invoker.** Most rows name the event and matcher the hook is registered on in `.claude/settings.json`. A few name an invoker instead: they are not registered on any event, and are called by path from an agent definition or another hook, so the page has no event section for them to live in. They are otherwise ordinary hooks.

The sourced libraries under `.claude/hooks/lib/` are deliberately absent. They are function modules with no event and no invoker of their own, loaded into the hooks above; the two shared-decision subsections below are where one gets documented when it is worth documenting.

### Source-edit safeguards (Edit|Write|MultiEdit)

- **`block-eslint-config-edit.sh`**: puts **every** edit to `eslint.config.{js,cjs,mjs,ts}` at any path to the operator, matching on the filename alone and emitting `permissionDecision: "ask"`. Reason: lint errors should be fixed in source code, not silenced in config. The prompt is deliberately broader than that rule, because judging what an edit changes does not separate the two cases: the legitimate shape and the silencing shape are the same shape. Adding a bare `...lint.<group>` preset spread is the `...lint.reactRouter` migration the CHANGELOG's **Action required** tells adopters to make, and it is also how a rule gets turned off, since ESLint applies later config objects over earlier ones and the preset groups overlap heavily rather than partitioning the rule space. `...lint.reactRouter` after `...lint.base` turns `no-empty-pattern` off; `...lint.storybook` after `...lint.react` turns `react-hooks/rules-of-hooks` off. Which of those an adopter intends is a fact about intent rather than about the edit's text, so no test over the text reads it, and asking is what follows: the separating property is held by the operator, so the call goes to them rather than being guessed or refused outright. Comparing the resolved configs before and after the edit does not recover a verdict either, it reproduces the same conflict one layer down, since the sanctioned migration is itself a severity drop (`no-empty-pattern` from error to off on a route file); the answer additionally depends on which files are sampled, reaching it means executing the config being judged, and a `PreToolUse` hook past its deadline is cancelled with no decision at all, so the write proceeds uninspected. What the guard owes in exchange for asking on the filename alone is a reason that admits it: the prompt is stated as being on the filename alone, the sanctioned migration is named, the common case is pointed back at the source file, and the operator is told the answer is theirs. The reason also refuses the workaround, telling the agent not to disable the hook; that clause is load-bearing rather than politeness, since no GAIA hook guards writes to `.claude/settings.json`, so the wording is the only thing between an agent that reads a prompt as an obstacle and silently removing the registration. An unreadable payload allows: with no `file_path` there is nothing to say the call even targets a config.
- **`block-manifest-write.sh`**: refuses writes to `.gaia/manifest.json` through `Edit`/`Write`/`MultiEdit` (no exemption) and through common Bash vectors (redirect, `tee`, `sed -i`, `sponge`, a `cp`/`mv` destination), honoring a `GAIA_MANIFEST_WRITE=` exemption marker on Bash commands. Registered under both the `Edit|Write|MultiEdit` and `Bash` matchers. The manifest is release-generated bookkeeping listing only the files GAIA ships; adopter feature work never adds to it.
- **`block-worktree-path-mismatch.sh`**: inside a linked worktree, denies an `Edit`/`Write`/`MultiEdit` call whose `file_path` resolves to the main checkout instead of the current worktree, the silent-wrong-write footgun where a stale pre-switch absolute path is a real, valid file in another checkout so the edit tools apply it with no error. Compares the toplevel that owns the common git dir (the main checkout) against the current toplevel; a target resolving to the main checkout is denied unless it falls under one of two exempt families (see [[Local Working State]]): the shared, symlinked `.gaia/local/` subdirectories, and the main checkout's `.gaia/local/plans/` and `.gaia/local/specs/` ledgers, which are exempt on the opposite rationale, they are not symlinked and have no worktree-side copy at all, so the main-checkout path is the only one that resolves to a real ledger and a plan run under worktree isolation writes its `PROGRESS.md` there by contract. A no-op outside a linked worktree. Fails open on any ambiguity (not a git repo, an unresolvable target directory).

**Payload `cwd` is per-agent, measured not documented.** Several hooks read the PreToolUse payload's `cwd` field as the acting agent's working directory, each falling back to the hook process's own working directory when the payload value is unusable. Measured on Claude Code 2.1.215 by instrumenting a hook to record its process cwd, `git rev-parse --show-toplevel`, and the full PreToolUse payload across three configurations:

| Configuration | hook process cwd | hook toplevel | payload `cwd` | `$CLAUDE_PROJECT_DIR` | `agent_id` |
|---|---|---|---|---|---|
| Main session, alone | main checkout | main checkout | main checkout | main checkout | absent |
| Subagent with `isolation: "worktree"` | its own worktree | its own worktree | its own worktree | **main checkout** | present |
| Main session write while a worktree subagent is concurrently alive | main checkout | main checkout | main checkout | main checkout | absent |

**`$CLAUDE_PROJECT_DIR` is the odd column out, and the one registration paths depend on.** Every other column is tree-scoped: a worktree session observes its own worktree in all three. `$CLAUDE_PROJECT_DIR` holds the session's original project directory and does not follow entry into a linked worktree, so in a worktree it names the main checkout while everything around it names the worktree. It is also absent from the Bash tool's own process; it is set for hook processes specifically.

That asymmetry decides how `.claude/settings.json` spells a hook command. Each one is rooted at the tree it belongs to:

```
"$(git rev-parse --show-toplevel 2>/dev/null || printf %s "${CLAUDE_PROJECT_DIR:-.}")/.claude/hooks/<name>.sh"
```

A bare relative path resolves against the Bash tool's working directory, which persists for the whole session, so a single `cd` leaves every script unfindable; `/bin/sh` then exits 127, which is neither 0 nor 2 and therefore does not block, and the guard layer fails open while every tool call proceeds. Rooting at `git rev-parse --show-toplevel` resolves to the current tree at any depth inside the repository, which keeps a worktree session on its own hooks. Prefixing with `$CLAUDE_PROJECT_DIR` instead would send a worktree session to the main checkout's copies, the same resolve-from-main shape the agent registry has. The variable earns its place only as the fallback for a working directory outside any repository, and the trailing `.` behind it is what keeps the worst case equal to a bare relative path rather than worse than one. `.gaia/scripts/check-hook-command-rooting.sh` holds the file to this shape.

Nothing at the registration site fails closed, because the failure being guarded against is a missing script and a missing script exits 127. The check reads the file, so it catches an unrooted registration there; a root that fails to resolve at runtime is outside what any registration-site spelling can reach.

**A registered hook is rooted; what it loads from disk after that is a separate question.** Once a hook script is running, it sources its own shared libraries (`.claude/hooks/lib/<name>.sh`) and reads the gate state it judges at paths rooted on `${BASH_SOURCE[0]}`, never on the working directory. A cwd-relative load or read is unfindable from any subdirectory the working directory has moved to, and the capability probe behind a library load treats a library it cannot find as a reason to stand down; for a blocking gate that is a silent fail-open rather than a diagnostic. Rooting on `${BASH_SOURCE[0]}` resolves to the acting tree the same way the registration form does, so a worktree session loads that worktree's own libraries and judges that worktree's own state. See `.claude/rules/shell-cwd.md` for what still holds this class down.

The third row is the contested case: the working directory is per-agent, not shared. The subagent's hook observes its own worktree while the parent's hook simultaneously observes the main checkout. Two facts close off the obvious alternatives: `session_id` is shared between a parent and its subagents (both report the same identifier, so nothing keyed on `session_id` can distinguish them), and `WorktreeCreate` fires under the dispatching session's `session_id` with no agent discriminator (its key set is `session_id, transcript_path, cwd, prompt_id, hook_event_name, name`, no `agent_id`, no `agent_type`).

The hooks reference documents payload `cwd` only as "current working directory when the hook is invoked" and says nothing about per-agent versus shared scoping, so this is measured behavior, not a guaranteed contract, and it is not assumed stable across harness versions. That is why a hook reading it pairs the payload value with a process-cwd fallback rather than depending on either source alone.

### Secrets safeguards (Edit|Write|MultiEdit)

- **`block-sensitive-read.sh`**: the whole tool-tier read guard for dotenv paths and for key, certificate, and credential paths; no `Read()` deny rule stands behind it. Two path classes, each with its own deny reason; an input matching both (`secrets/.env`) is judged dotenv first, and across a Bash command the dotenv and environment-dump rulings come before the secret-path one. The dotenv class denies `.env` and every `.env.<env>` variant (`.env.local`, `.env.production`, nested copies) while allowing `.env.example`. The secret-path class denies any path whose basename ends `.key` or `.pem`, whose basename contains `credential` case-insensitively, or which sits anywhere under a directory named `secrets`. On the `Read` matcher it judges `file_path`. On the `Grep` matcher it judges `path` and `glob`, because the Grep tool returns file contents in content mode and so reads a path exactly as Read does. On the `Bash` and `Monitor` matchers (a Monitor command is judged exactly as a Bash command) it denies readers, sourcing, redirection, and bare environment dumps (`env`/`printenv`); it allows `env NAME=value <cmd>` and benign non-reading commands that merely name a protected file (`cp .env.example .env`, `ls -la .env`, `grep '.env' .gitignore`, `grep server.key .gitignore`). The grep family is covered through the operand grammar in `lib/reader-operands.sh`, which skips the pattern operand so those last commands stay allowed while `grep -r TOKEN certs/server.key` is denied. The deny reason is fixed and never echoes the matched command, so an inline secret in the command string cannot leak into the transcript. Always `exit 0`; the decision travels in the stdout JSON. Registered under the `Read`, `Grep`, and `Bash|Monitor` matchers.
- **`lib/reader-operands.sh`**: the grammar the read guard sources, answering one question, which tokens in a command segment name or select a file a reader will open. The grep family needs real argument grammar rather than a token sweep, because `grep PATTERN FILE` puts a non-path in first position. A filter flag whose glob selects the files a recursive search reads is judged like a path, matching the Grep tool arm's reading of its `glob`: each element of a comma-separated list on its own, since ugrep (the `grep` Claude Code's shell runs) reads the value as one, skipping an element that starts `!` or `^`, which ripgrep and ugrep read as an exclusion. Its flag tables are the union of GNU grep's and ripgrep's, which is safe only while no discard-listed flag is value-less for either tool: a flag that takes no value for the tool actually invoked eats the pattern, the path is then consumed as the pattern, and the walk emits nothing at all, which is a silent allow rather than an over-deny. `-r`, `-T`, and the bare `--color` / `--colour` spelling are excluded from the tables for exactly that reason. The hook emits a structured deny rather than exiting non-zero when it cannot load it, because a non-zero exit other than 2 is non-blocking and would let every secret read through.
- **`block-secrets-write.sh`**: denies a write whose target basename is `.env` or `.env.<anything>` (allowing `.env.example`) before any content is read, with a fixed message saying `.env` files stay gitignored and are edited manually by the developer; this pairs with the `Edit(.env)` deny rule in `settings.json`, which matches only the literal name. For every other path it scans `new_string` / `content` / MultiEdit `edits[].new_string` payloads for secret-shaped values (AWS access keys, GitHub PATs, PEM private-key headers, dotenv-style `_TOKEN` / `_SECRET` / `_KEY` / `_PASSWORD` assignments with non-placeholder values). A leading `export`, `declare`, `typeset`, `local`, or `readonly` does not take the line out of the scan, and neither do that keyword's own options, so `declare -r` and `local -r` are scanned like the bare forms. Allows known placeholders (`changeme`, `${VAR}`, `$VAR`, etc.) plus three whole-value shapes: a single unnested `$(…)`, a `<…>`, and a `your-…` / `fake-…` / `dummy-…` / `example…` placeholder. Because a shell declaration reaches this rule too, the ordinary expansion forms are allowed as whole values as well: a positional in either spelling, an expansion with an empty operand, a value that is nothing but braced references, and an expansion followed by a path (`$1`, `${1}`, `${VAR:-}`, `${A}${B}`, `${ROOT}/dev.pem`). A non-empty default is not, since that is where a real secret would sit. The path arm bounds each segment of the suffix, so `${ROOT}/dev.pem` passes while `${ROOT}/<a-literal-key>` does not: the separator buys a path, not an unbounded tail. A shell line's trailing comment or `;` / `&&` / `||` clause is dropped before the value is read, so an ordinary `export FOO_KEY="$BAR" # note` is not mistaken for a literal; the tail is still read on its own terms, and secret-shaped material parked in it is denied, since a comment beside a placeholder is where a real key lands. Every arm reads the shape of the value, never its meaning: a substitution that prints a secret is allowed, and a short enough secret behind a placeholder prefix still fits. The guard is a write-time heuristic, not a proof that the value holds no secret. A write whose destination is exactly `.env.example` (matched by basename) drops the placeholder allowlist for the assignment rule and judges the value by shape alone, the same way its own dotenv path deny and `block-sensitive-read.sh` special-case that file: it is a committed file whose purpose is to carry placeholder assignments, so the general allowlist's job (recognizing placeholders) is redundant there, while the shape test (a 13+ alphanumeric run mixing letters and digits) still catches a pasted key. The three pattern rules (AWS, GitHub PAT, PEM headers) still run on the file unchanged. Because the bound is on the run rather than the value, a segmented secret (a UUID-format key, a base64 value broken by `/` or `+`) clears in this file even though the same value is denied everywhere else.

**The `.env` read boundary, stated honestly.** GAIA's shipped `permissions.deny` carries no `Read()` rule at all, so the shipped hooks are the whole tool tier: `block-sensitive-read.sh` for dotenv paths and for key, certificate, and credential paths, across the `Read`, `Grep`, `Bash`, and `Monitor` matchers. It is heuristic, command-string-based defense-in-depth, not a sandbox. Several surfaces stay open by design, and what follows is the set known to be open rather than a closed one: **MCP shell execution** (e.g. Serena's `execute_shell_command`), best closed at `.serena/project.yml` via read-only mode, ignored paths, or excluded tools; **arbitrary subprocesses** (a Node or Python script that opens `.env` itself), invisible to any hook; **deliberate command obfuscation**, out of the threat model; and **a quoted path containing a space**, which the operand walk splits into fragments before quotes are stripped, so `cat "my file.key"` is allowed where the backslash-escaped spelling is denied; and **a search filter glob that only expands onto a secret** (`--include='*'`, a brace glob), since a glob is read by the path predicate and only its literal shapes match, and file selection spelled as a type rather than a glob (`rg --type-add`), which is not read at all. The hook header carries the same list, and that is where a newly found spelling is recorded first. The layer that does reach an arbitrary subprocess is the OS-level sandbox, and GAIA declares it: `sandbox.filesystem.denyRead` in `settings.json` covers the dotenv and secret classes and blocks all sandboxed processes from them. Those entries stay inert until a machine enables the sandbox, which GAIA does not do by default; see [[OS Sandbox]]. Declaring the boundary there rather than as a `Read()` deny rule is what keeps Claude Code's bypass-immune approval breaker disarmed, since that breaker arms on the presence of any `Read()` rule whatsoever.

### Bash safeguards (Bash, Monitor)

Each script reads `tool_input.command` from stdin and filters by content; there is no `if:` annotation on the hook entry. The matcher names both tools that carry a shell command in that field, for the reason "Which tools a command-reading hook binds" below states.

- **`block-no-verify.sh`**: denies `git commit` or `git push` carrying a hook-bypass token: `--no-verify` or a `-c core.hooksPath=` redirect. Also denies `git commit -n` (short form of `--no-verify`); `git push -n` (dry-run) stays allowed. Foreign-repo commands pass via the shared repo-scope helper. The hook walks command-position segments so a `-n` on another program (`grep`, `head`, `sort`, `tail`) is inert. Keeps an unambiguous whole-command fail-closed net for the tokens that cannot appear anywhere else (`--no-verify`, `core.hooksPath=`).
- **`block-main-destructive-git.sh`**: denies (1) `git commit` while HEAD is `main`/`master`, (2) force-push to `main`/`master`, and (3) a push whose destination is `main`/`master`, either a plain push while HEAD sits there or a refspec naming it explicitly from any branch (PR-only flow, closes the "forgot to switch branches" footgun, and the refspec form the "wrong destination from a feature branch" one). A commit or push whose directory word the guard cannot read is denied too, when a checkout that word could name is on `main`/`master`; a word it *can* read names the checkout outright, whatever repository that is. Walks command-position segments so `git commit` text in an argument or a different program's flag does not trigger a false deny. Authoritative rule: [[Git Workflow]]. It also denies a peer session's checkout or switch that would move the main checkout's HEAD off a branch holding an open pull request, the precondition [[PR Merge Workflow]] sets for picking a cleanup arm; the session that opened that pull request passes, anything the guard cannot check (`gh` unreachable or slow) fails open, and the hook's source describes the kinds of spelling it cannot see.
- **Shared command-word reading**: `block-no-verify.sh` and `block-main-destructive-git.sh` both read command words through `.claude/hooks/lib/git-segments.sh`, loaded fail-closed, and the destructive-git guard skips the directory resolution for any git subcommand other than `commit` and `push`.
- **`block-rm-rf.sh`**: denies catastrophic `rm -rf` patterns: `--no-preserve-root`, absolute paths, `~` / `$HOME`, `.`, unscoped `*`, `.git`, `.claude`, `node_modules`. Allows the scoped scratch paths `.gaia/state-registry.json` declares in its `rm_whitelist`, each in both its relative and its absolute spelling, so the guard accepts the absolute form `.claude/rules/shell-cwd.md` requires of every Bash call. The absolute-path deny names those scratch roots, so a denied absolute removal carries its next step. An absolute path carrying a `..` segment is denied rather than whitelisted, since it resolves somewhere its spelling does not name. Judgment is per-segment and each segment must carry its own `-r`/`-f`, so an unflagged `rm` quoted as prose is not denied on the strength of a real removal elsewhere in the same command. A flag is recognized only as its own shell word, so a hyphenated path component ending in `r` or `f` (`my-matcher`, `feat-perf`) is not mistaken for one. It remains a heuristic text matcher and is porous by construction; its header states the standard for reporting a hole.
- **`capture-red-observations.sh`** (PostToolUse and PostToolUseFailure, Bash): on a one-shot vitest run, passing or failing (a failing run exits non-zero, which Claude Code reports through PostToolUseFailure only), re-invokes vitest with `--reporter=json` scoped to the agent's target, records each genuinely-failing per-test result to the RED-observation ledger (`.gaia/local/red-ledger/`). Records file, full test name, content signal, and failure kind. Collection/compile errors are excluded. Observe-only; always exits 0. See [[TDD RED Verification]].
- **`red-verify-commit-check.sh`** (PreToolUse, Bash deny): before each `git commit`, checks every new-at-HEAD test file against the RED-observation ledger. ### Workflow-boundary safeguard (Bash, Agent, UserPromptSubmit)

- **`audit-loop-bound.sh`** (PreToolUse deny on `Agent|Task`): also gates a dispatch of `audit-loop-unit` on the main session's context reading and records the unit window that nested member dispatches run inside. It denies a dispatch of a `code-audit-*` member on a new tree once the branch's recorded rounds reach the allowance, or earlier when the evidence says the rounds stopped converging, and records each allowed round in a per-branch state file under `.gaia/local/protected/audit-loop/`. The deny message carries the grant and accept lines a human types to continue. The hook is registered on no SessionStart event, so `/clear` and compaction leave the branch state untouched. See [[PR Merge Workflow#The branch checkpoint]].
- **`audit-loop-ask-grant.sh`** (PostToolUse on `AskUserQuestion`): records a selection of the checkpoint question the bound hook pinned whole in guarded state, so Claude authors no option. It records only when the payload has no `agent_id`, the session is interactive, `permission_mode` is one measured as waiting for a human, the branch has one pending checkpoint carrying a question, the payload's `tool_input` (minus the `answers` and `annotations` the harness adds) equals that question, and the answer is exactly one pinned label. `Stop and file the remainder` and `Type audit-accept instead` record nothing; every other decline is a visible `systemMessage` naming the typed fallback. It never exits 2, and `block-audit-loop-write.sh` denies any Bash or Monitor command that executes it. See [[PR Merge Workflow#The branch checkpoint]].
- **`audit-loop-grant.sh`** (UserPromptSubmit): the writer, with the recorder above, of the allowance half of the branch state; it owns the typed lines, which stay the fallback and the deliberate human override. It records an answer only when the whole typed prompt is exactly `audit-grant <n>` or `audit-accept`, in an interactive session (the hook's environment carries `CLAUDE_CODE_ENTRYPOINT=cli` and no transcript record names another entrypoint, so a nested or resumed `claude -p` session cannot record a grant), with a checkpoint pending for the branch. Any other prompt that mentions either word is rejected visibly and records nothing. See [[PR Merge Workflow#The branch checkpoint]].
- **`block-audit-loop-write.sh`** (PreToolUse deny on `Edit|Write|MultiEdit`, `Bash` and `Monitor`): refuses any write that targets `.gaia/local/protected/` as a whole or the context readings, and any execution of the two audit loop recorders, so Claude can neither raise its own allowance, reset the history, nor move the checkpoint line. It is a text guard over the natural spellings of a write; the hook header lists the spellings it covers and its limits. See [[PR Merge Workflow#The branch checkpoint]].
- **`block-handrolled-pr-poll.sh`** (PreToolUse, Bash and Monitor deny): denies a shell loop that polls `gh pr view` for PR state, or `gh pr checks`, without reading `mergeable` anywhere in the command, and names `.gaia/scripts/pr-wait-merge.sh` in the denial. A wait that exits only on `MERGED` cannot end once the base branch has landed a conflicting change: the queued `--auto` merge never lands and the loop spins until a human notices. Two escapes, both cheap: a command that already reads `mergeable`/`CONFLICTING` passes however it is spelled, and so does one naming `pr-wait-merge.sh`, which covers the blessed path and any command quoting the shape while writing about it. It requires a loop keyword at a command position (after a separator or a newline, so multi-line commands are reached) *and* a `done`, which is what keeps it off prose mentioning a poll inside a `--body`. It binds both tools that take a raw shell command in the same `tool_input.command` field, so the shape is not armable from the tool beside the one the guard watches; a `Monitor` call carrying `ws` rather than a command is not a poll and passes. A text heuristic over an unbounded surface, the same posture `block-manifest-write.sh` takes: a poll written in Python, or inside a script file, walks past it. See [[PR Merge Workflow#Post-merge verification before cleanup]].
- **`block-invalid-pr-title.sh`** (PreToolUse, Bash deny): runs the repository's own commitlint on `"<title> (#<number>)"`, the string the `PR Conventions` check lints, before a `gh pr create` or `gh pr edit` reaches GitHub. The ` (#N)` suffix counts toward the header limit, so a title that passes as a commit subject can still fail CI; this catches it while the PR does not yet exist. The number is the real one for `gh pr edit <N>` and, for a create, one past the highest squash suffix in recent history. It reads each top-level command of the call with the shared shell-word scanner, skipping heredoc bodies the arming walk proves are data, and denies `--fill` without `--title`. It leaves to CI a title the shell expands, a PR in another repository (`--repo`), a `gh pr create|edit` nested in a substitution, subshell or compound-command body, a checkout with no commitlint installed, and a commitlint that cannot run (only its own problem report denies). See [[Naming Conventions]].

### Session-entry maintenance (SessionStart, PostToolUse)

Neither of these denies anything; both repair state that a session's entry point is the only occasion to fix.

### Shared verb-arming decision

Bash-matcher hooks decide whether a tool call carries an invocation of a verb they care about (`gh pr merge`, `gh pr create`, `git commit`/`push`, `gh issue create`/`edit`/`close`/`reopen`) through one shared library rather than a private pattern pair apiece. The decision runs in three passes. First, a raw text match against the whole command string: the verb at the start, after a list operator or newline, or after a command or process substitution opener (`$(`, a backtick, `<(`, `>(`), since the shell runs what follows one; `$(` and a backtick run inside double quotes too, and the match arms on every opener in either position, fail-closed. Second, on a raw hit only, a same-length view of the command is built in which every heredoc body proven to be inert data is masked out (written with `cat` or `tee` to a plain file, no expansion on the opener line, an unambiguous delimiter that actually closes later in the text, and a body with no command substitution in it unless the delimiter is quoted, since the shell runs one there; the walker's own header names the openers it checks), and the same match runs again against that view; a heredoc body carrying a merge command no longer arms a hook on its own. A substitution opener must also be live there: a second same-length view masks every opener the shell never runs (inside single quotes, behind a backslash, or in a quoted-delimiter heredoc body read by a bare `cat` or `tee`, the usual way a pull-request, issue, or commit body is passed), and an opener arms only if it survives that view as well. The walker file's header states the exact shape and what it abstains on. Third, a tokenizer reads the shell's own first command and arms on the verb regardless of how its characters are quoted, closing the gap where a quoted verb defeated every text match. **Wherever the decision cannot tell, it keeps the raw-match answer**: an uncertain input never trades a possible over-arm for a possible miss.

The adopting hooks are the root `.claude/hooks/*.sh` files that load `lib/verb-arming.sh`; `grep -l 'lib/verb-arming.sh' .claude/hooks/*.sh` lists them. Whether one can deny an armed call outright is stated in its row of the index at the top of this page.

Four residuals survive the shared decision, all fail-closed:

- A quoted string carrying a separator or substitution opener ahead of the verb still arms every hook; there is no safe narrowing. The common case is a pull-request or issue body that cites a command in backticks, which trips the merge gates on a command that merges nothing.
- A verb whose characters are quoted still slips past outside the first command, since the tokenizer pass reads the shell's first command only.
- A dollar-quoted word (`$'…'`) is unmodelled; the decision abandons suppression on one rather than approximate it.
- The tokenizer's bounded read of the first command's opening characters can itself create an arm no data proof removes, when truncation at that bound leaves a word reading as the verb.

### Shared jq-availability decision

A hook reads its payload with `jq`. On a machine with no `jq` on `PATH` that read ends the script at status 127 before the payload has been looked at, and the PreToolUse contract blocks only on exit 2 and treats every other non-zero status as a non-blocking error. So the call the hook was written to deny proceeds, with no denial and no diagnostic, and the whole fail-closed layer goes inert at once while the advisory hooks correctly no-op.

Every blocking PreToolUse hook therefore reaches one shared arm before its first `jq` call, and refuses with exit 2 rather than falling through. The refusal cannot route through a hook's own `deny()` helper, which builds its JSON response with `jq`; the exit-code contract needs no interpreter at all.

The arm refuses **narrowly** where the hook's matcher can reach the `jq` install itself. A hook that cannot read its payload also cannot tell whether the call is one it binds, so an unconditional refusal on a `Bash`-matcher hook would deny every command in the session including the one that repairs the machine. Such a hook passes the literals whose absence from the raw payload proves the call sits outside its remit; absence allows. Presence is not proof of membership, and that over-deny is the safe direction. A hook whose matcher cannot reach the install refuses unconditionally within that matcher.

An **advisory** hook takes the opposite arm and stands down, because a lost reminder costs less than a blocked session.

Bash-path hooks read their common payload fields through `.claude/hooks/lib/hook-payload.sh` in one `jq` process, after the jq-availability arm. A blocking hook that cannot load that library refuses; an advisory hook exits 0. A field outside that set keeps its own `jq` read.

`.claude/hooks/lib/jq-availability.sh` owns the arm and the literal contract; each hook states beside its own call which spellings its literals cannot reach.

### Which tools a command-reading hook binds

A matcher is an unanchored regex over the **tool name**, so `"Bash"` selects the `Bash` tool and nothing else. More than one tool hands a hook a raw shell command in the same `tool_input.command` field and runs it in the same shell environment, and `Monitor` is the second one.

Every **blocking** command-reading hook's `PreToolUse` registration names `Bash|Monitor`. `block-no-verify.sh`, `block-main-destructive-git.sh`, and `block-rm-rf.sh` carry no `tool_name` test at all, so they act on a call through either tool; `block-handrolled-pr-poll.sh` acts on both too. Every other blocking command-reading hook admits `Bash` alone in its own `tool_name` test and stands down on a call through `Monitor`. An **advisory** command-reading hook (`token-tally-git-op.sh`, `post-findings-block-on-merge.sh`) registers on `Bash` alone.

## Why `.claude/rules/shell-cwd.md` bans `cd`

The directive is about the guard layer, and a `cd` takes it down without announcing itself.

**Into another checkout, the registrations re-root.** `.claude/settings.json` roots every hook command at `$(git rev-parse --show-toplevel …)`, derived per invocation rather than pinned, so the working directory picks the checkout. A sibling clone has no hook scripts, so `/bin/sh` exits 127, and because 127 neither blocks nor is reported the whole `PreToolUse` layer fails open silently; one of this repository's own linked worktrees under `.claude/worktrees/` is a different checkout at a path *inside* this one, and runs that branch's guards rather than the ones under review. `.gaia/scripts/check-hook-command-rooting.sh` holds the registration form, not the runtime cwd, so nothing at the registration site can close either case.

One neighbouring mechanism is closed rather than live, and it is worth knowing which: the hooks locate the framework code they load and run from their own on-disk location, so a `cd` does not reach that path. A `cd` reaches the re-rooting above unchanged, which is enough on its own, because that one fails open across every `PreToolUse` guard at once rather than one gate at a time.

GAIA maintainers: what holds that rooting down is `.gaia/scripts/lint-hook-cwd-relative-loads.sh`, which reds when a hook reintroduces the class. That compounds with the ordinary cost of a `cd`: the working directory it sets persists for the rest of the session, so every later relative path resolves against it.

## Adding hooks
